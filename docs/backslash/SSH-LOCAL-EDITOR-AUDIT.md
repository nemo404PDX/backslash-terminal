# Independent SSH local editor design audit

Audit date: 2026-10-13 UTC. Scope: source/documentation inspection and this report only; no build, install, host probe, shell configuration or implementation. Target: Windows Terminal stable v1.25.2733.0, commit `dc8ae365847d41f62d1ebca93815bb00959bc12f`.

## Verdict and evidence limits

**Proceed to narrowly scoped capability proofs, not general implementation yet.** A client-owned command buffer with inline completion and local upward presentation is plausible. The unresolved problem is the contract connecting that editor to a live persistent remote shell: readiness, exact submission, echo ownership, interactive handoff and trustworthy outcome correlation. Neither a terminal screen cursor nor switching SSH libraries supplies that contract.

Native shell mode remains a supported path. A pill/centered popup is superseded and is not an audit recommendation. No blanket impossibility finding is warranted; support may be proven for a defined shell/integration contract before arbitrary shells.

## Architecture choices and unresolved contracts

1. **External ssh.exe plus a client editor:** closest to baseline and retains existing OpenSSH authentication/config/agent behavior. It provides a live PTY stream, not remote channel metadata. Prove a shell adapter/readiness contract first. Sending a bootstrap automatically can remove manual setup while still executing remote code; this is a separate explicitly described capability.
2. **Embedded SSH transport:** can expose authenticated peer identity, channel lifecycle and direct resize/input control. It adds authentication, host-key, proxy/agent and maintenance work. It does not discover cwd or individual command results inside a persistent shell. Evaluate only if a demonstrated external-process limitation justifies the cost.
3. **Per-command exec channels:** useful for bounded queries or independent commands, but transport reuse does not share cwd/environment/jobs with the interactive shell. Do not silently replace the requested persistent shell. A stateful remote service would be a new remote-code architecture.
4. **Native integrated shell mode:** preserves shell editing/completion and supplies optional marks. Keep it available while supported local-compose contracts mature. Manual recall is a useful fallback, not evidence that the preferred inline behavior is delivered.

[SSH RFC4254 sections 6.5, 6.7 and 6.10](https://www.rfc-editor.org/rfc/rfc4254.html#section-6) define shell/exec requests, resize and program termination status. A persistent shell's channel termination result is not a result per entered line. [OpenSSH's manual](https://man.openbsd.org/ssh) also documents client escape handling, which must be considered for commands beginning with tilde. [ConPTY documentation](https://learn.microsoft.com/windows/console/pseudoconsoles) establishes a UTF-8 character channel. [Microsoft shell integration](https://learn.microsoft.com/windows/terminal/tutorials/shell-integration) requires shell cooperation and documents optional exit status; its examples do not establish automatic remote integration.

Proposed state contract: authentication/native → verified prompt-ready/local-compose → frozen submission/remote ownership → executing or interactive pass-through → correlated completion and fresh prompt-ready. Ambiguity suspends automatic composition and never causes a replay. Ctrl-C cancels locally during composition by a defined policy; during execution it goes through native terminal input. Mode changes must preserve pending IME/composition, selection and pasted text. Nested SSH changes the effective context; do not inherit outer host/user/shell attribution without explicit evidence.

History scope should default to the confirmed host/user/shell identity with cross-directory reuse; cwd is ranking/context metadata, not a hard silo. Broader search is explicit. If identity is only an alias, label that provenance and avoid silently merging it with authenticated identities. Per-execution result must survive repeated identical text with differing outcomes. Define success semantics for pipelines/pipefail, compound commands and background jobs; foreground submission success is not proof every later job succeeded. Interrupted/disconnected executions remain non-success unless reliable evidence completes them.

None was run under this documentation-only scope. Future tests should retain input byte traces, parsed-grid snapshots, local-editor revisions/state transitions and execution records; screenshots alone cannot establish input isolation or reliable status.

| Gate | Smallest useful fixture | Pass evidence / failure |
| --- | --- | --- |
| A: local isolation/geometry | Deterministic connection fixture; wrap prompt at right edge; grow multiline completion beyond viewport; select/copy/click and IME | Zero outbound composition/layout bytes; unchanged remote grid/cursor/dimensions; correct transformed cell hit-tests and local caret. Any fake newline/scroll or copy corruption fails. |
| B: concurrency/reflow | Inject job output, cursor moves, erase, wide text and resize during compose; user browses older scrollback | Buffer/revision preserved; deterministic reanchor/suspend; no jump that loses input or mutates remote text. Stale anchor or lost selection fails. |
| C: persistent shell/exact submission | One supported controlled shell: cd/export/function, then subsequent command; heredoc, quoted newline, CRLF paste, incomplete syntax and leading tilde | Reviewed text and deliberate execution count match; same shell state preserved; no newline execution before Enter. Prove bracketed paste on/off and shell bindings. Byte write success alone is insufficient. |
| D: echo/handoff | Echo on/off; concurrent matching output; pager/editor, normal-screen REPL/read, password prompt, Ctrl-C and nested SSH | Visible command reconciles once without discarded remote output; correct input owner; secrets absent from editor/history; return only on supported boundary. Alternate screen alone cannot pass. |
| E: outcome integrity | Success/failure/absent status; same text repeated; forged OSC D; duplicate/out-of-order marks; disconnect before/after write | Exactly correlated records; only accepted confirmed-success evidence eligible; Unknown never promoted by forged/uncorrelated messages; no automatic replay. |
| F: Unicode/completion | Combining marks, surrogate pairs, ZWJ emoji, CJK/ambiguous width; edit mid-buffer while reply arrives | Grapheme-safe motion/delete and exact preserved text; range/context/revision validation rejects stale result. Number of code units must never stand in for cells. |
| G: durable policy | Two windows ingest simultaneously, restart/crash during pending result, change storage/suggestion modes, cross-directory and broader search | Stable execution IDs/no lost or duplicate records; immediate completed-record visibility; required scope; success-only excludes Unknown/Failed; disabled storage does not capture new records. |
| H: no manual setup | Clean supported disposable remote with no existing plugin; restrictive shell; bootstrap failure | Document exact remote code/files/env effects and cleanup; successful first connection without manual host edits, or explicit native/limited capability fallback. Do not claim zero remote code from zero manual steps. |

Recommended order: A/B without a host, then C/D/E on a separately authorized disposable supported shell, then F/G/H. Commit to product implementation only after the relevant gate has measured evidence. Broader shell coverage follows explicit compatibility results rather than a universal promise.

## Audit delta and remaining research

The inspected draft already correctly separates local presentation from remote grid, persistent-shell status from SSH channel exit, and no manual setup from no remote code. This audit strengthens acceptance around forged provenance, command replay ambiguity, transformed accessibility/IME/hit-testing, exact text persistence and lock/blocking behavior. No contradiction requires rejecting the preferred UX.

Still missing: a tested shell-specific submission/bootstrap protocol; threat model for reported metadata; concrete presentation geometry/scrollback interaction; completion range unit contract; remote completion query side effects/context freshness; history schema/concurrency/storage-policy semantics; compatibility matrix and captured runtime traces. Static symbols identify seams but do not settle those questions.
