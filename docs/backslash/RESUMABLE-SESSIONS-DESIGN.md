# Resumable remote sessions - future design

[Project entry point](README.md) | [App commands](APP-COMMANDS-DESIGN.md) | [Saved groups](SAVED-TAB-GROUPS.md) | [Shell/session boundaries](SHELL-PRODUCTIVITY.md)

## Status and user intent

Design only; no helper, remote command, installation, service, credential access or connection was performed. Name this **resumable/persistent session**, not a new encryption protocol. Explicit opt-in chooses Normal or Resumable connection. Ordinary SSH connect, disconnect, shell exit or tab close must not silently create persistent remote ownership. Saved groups are local launch/layout templates and currently create fresh local terminals/connections; they do not preserve a running process, remote PTY, output or ownership. A profile's already configured launch command can have its own remote behavior, but that is not a group persistence guarantee.

The goal is a remote owner/state that remains after SSH loss, so the same authenticated user can resume live work or immediately receive its completed/failed result and missed output. Starting that owner via a command is valid; a permanently installed system service is not mandatory. Reboot survival is not promised.

## Unix already has survival mechanisms

Noninteractive jobs can be arranged to continue after logout using hangup handling and proper stdin/stdout/stderr routing. [GNU nohup](https://www.gnu.org/software/coreutils/manual/html_node/nohup-invocation.html) ignores hangups and manages terminal stdio; launching it in the background and choosing logs are separate shell decisions. [Bash signals/disown](https://www.gnu.org/s/bash/manual/html_node/Signals.html) describes removing a job from the job table or marking it not to receive the shell's hangup forwarding. A background job alone is not an unconditional survival guarantee. [systemd-run](https://www.freedesktop.org/software/systemd/man/systemd-run.html) supports managed transient jobs; user-manager/logout policy must be checked, not changed silently. These are job survival/logging mechanisms, not automatic interactive PTY reattachment.

[tmux's manual](https://man.openbsd.org/tmux.1) describes a separate server owning PTYs/sessions and clients that detach and later attach, including after accidental SSH disconnection. It is one supported remote owner candidate, not the only solution and not a prerequisite for every persistent job. Backslash could arrange a selected supported mechanism through an explicitly enabled connection workflow. Existing tools versus a custom helper require capability, policy, packaging and licensing decisions. Windows remote ownership/PTY backend remains unresolved; do not claim tmux portability there.

## On-demand owner proposal

Investigate a remote user process/helper retaining a PTY and bounded session/output state in memory, started only when requested and cleaned up by an explicit lifecycle policy. Avoiding a permanent service does not avoid remote execution/setup, executable/interpreter requirements, temporary files, permissions or policy checks. Memory-only is not a security guarantee and cannot make results durable after owner/process loss without separate storage. Define ownership, authenticated IPC/access controls, allowed session operations, bootstrap verification, stdio detachment, orphan handling, resource quotas, platform capabilities and cleanup before any prototype. No automatic installation or global shell/service/security change.

Offer start in named persistent session, remembered-session selection and explicit discovery/attach to other accessible sessions. Show actual capability and Normal/Resumable state. Already-running arbitrary processes outside a managed persistent session cannot be promised safe retroactive adoption; job-control, controlling-terminal reassignment, permissions and platform limitations need research. Prefer creating supported ownership before starting the job. Authentication stays with the chosen SSH/agent/config backend; session management does not copy private keys/passwords into its registry.

## Identity, registry and input ownership

Use distinct identities: authenticated remote host/account; durable opaque remote session ID; client installation ID/friendly device label; stable runtime tab ID; stable per-pane/connection attachment ID; containing window/process ID; saved group template ID. Window/process is a container, not an attachment's durable identity. Tab/pane tear-out or reparenting carries identity and control association; duplication creates new local identity and must not silently duplicate controller ownership. Current [TerminalPaneContent](../../src/cascadia/TerminalApp/TerminalPaneContent.cpp) emits ContentId only for move/content operations, and [TerminalPage](../../src/cascadia/TerminalApp/TerminalPage.cpp) plus [TabManagement](../../src/cascadia/TerminalApp/TabManagement.cpp) implement move/remoting seams. Cross-process handoff needs source-backed transport/lease investigation; an in-memory object cannot be assumed to survive it. Group recipe focus IDs are layout-relative ordinals, not these durable runtime IDs.

Two ordinary connections to the same host/account with separate shells are independent and both writable. Only multiple attachments to the **same persistent session ID** need shared input ownership. First-version recommendation: one controller, other attachments viewing. Viewers can scroll/search/copy; explicit Take control transfers input without closing the original or requiring reopen/reconnect. Server-confirmed lease/release drives typing capability; a stale reconnect cannot reclaim control silently. Simultaneous collaborative input is a later opt-in choice.

Show session name plus Controlling/Viewing on same-session tabs and per-pane role badges for splits. Controller detach/close releases control; viewers show Viewing / Control available and still require explicit Take control. Unexpected loss remains pending until server release/lease expiry is confirmed. Ending a session updates every attachment to Ended with retained output. Test live role propagation on one laptop, multiple windows and multiple computers.

All windows sharing a Backslash data root should coordinate a local registry of remote identity/session ID, stable local attachments and last-known state/time. Portable storage preserves that list across launches; no cloud or multi-machine sync is assumed. Local runtime owner is authoritative about actual local attachments, remote owner about remote job/control. On launch reconcile crashed/stale local records and mark remote status unverified until an authenticated check. Transactional writes, IPC, multiple processes, crash recovery, tear-out and copied portable-folder installation-ID duplication need tests. Keep this registry separate from saved group templates.

An ID/hash/username hash or friendly device label identifies/selects; it does not authenticate or encrypt. Default UI lists own-created/explicitly attached sessions, with deliberate discovery and attach/control for others the account can access. Filtering is not security. Same OS account often can access same-user resources; genuine multi-person isolation requires separate OS identities or an enforcing separately authenticated service. Simple remembered-own-session scope must state that limitation; enterprise identity/ACLs are future work. Remote access controls, encryption at rest and key lifecycle are separate design decisions.

## Lifecycle and detached grace proposal

Distinguish shell exit, client close, transport loss and session-owner termination. In Resumable mode, Detach releases the client/control lease while preserving supported work; End session requests termination of that specific owned session; close-tab offers Detach / End / Cancel. Normal connections keep their ordinary behavior. Network loss does not prove a command stopped or completed. An interactive shell's zero exit status is not proof all children/background jobs ended; idle output is not completion or reliable waiting-for-input detection. Capability-based status may say unknown when unsupported.

Candidate policy: detach starts a server-side grace timer; successful reconnect cancels/resets it. Expiry permits live-session cleanup only after tracked work completes, preserving still-running jobs. Distinguish interactive shell idleness, foreground job result and child/background-job ownership. Define what work is tracked and which completion evidence is authoritative. An optional separate explicit hard lifetime limit can interrupt work and must disclose that risk; default forced kill is not proposed. Durations/defaults remain undecided. Timers must continue without the client and use server monotonic time/generation guards. Test reconnect vs expiry vs completion, duplicate detach/end requests, controller lease expiry, graceful shutdown versus forced termination, and partial failure.

## Managed record and preserved output/results

Preserving output the user would see while connected is core functionality of the opt-in Resumable session. Maintain unique session ID scoped to authenticated host/account, remote boot/owner generation to prevent reuse confusion, sequence/offset state, bounded missed output and trusted completion/failure result. Local last-known state and timestamp remain distinct from verified current state. Optional authenticated polling can update it; unreachable means unverified/unknown, not invented current status.

Reconnect queries the same ID: resume live or immediately surface Completed/Failed while detached, with exit status/time, missed output and bounded tail plus full retained-log access. Do not bury detached failures or retry commands automatically. Show explicit truncation/gaps/rotation and the actual retained range. List running/detached/completed records with last-known times and reconnect/end/dismiss actions. Keep acknowledgement/dismissal separate from remote termination and log deletion.

Separate live PTY/helper cleanup from durable result retention. Deliberately configured remote storage can retain results after the helper exits; a memory-only owner cannot provide durable records through its crash/reboot without external storage. Record crash/reboot/network ambiguity as Unknown with available partial output, not inferred success/failure. If saving a log fails, show failure and remaining in-memory evidence; do not claim durable success. Define result acknowledgement, retention/rotation/size limits, quota behavior and cleanup policy before rollout. Bounded output preservation and access controls protect later access/storage; they are not a reason to withhold the user's output. Never record authentication input/passwords or private keys. User-visible command output can contain sensitive material, so storage permissions, user-controlled retention and encryption/key management need an explicit contract, without pretending a hash encrypts it.

## First prototype and open questions

First acceptance: one explicitly managed tracked job survives disconnect, completes, and reconnect to the same authenticated session ID immediately presents the result and missed output. Then test interactive PTY attach, supported waiting/input status, background children, wrong account/host, reused boot/PID/session generation, multiple viewers/control transfer, crashes, output gaps, durable result after owner cleanup, denied policy/authentication, unavailable backend and Windows limitations. Native local pane operations require no persistence owner.

Backend selection, bootstrap delivery, remote policy permissions, named discovery, control lease policy, quotas, timings, durable storage and encryption remain open. Do not implement them through ordinary saved-group actions or arbitrary commands injected into an active SSH stream. Capability probes/setup/agent handling require explicit future authorization and tests; none occurred in this documentation pass.

## Scope refinements: control lock and presence

Viewing/control governs input from multiple attachments to the exact same PTY/shell/program. It is not a directory lock and provides no file-write concurrency protection. Separate shells in the same directory remain independent/writable. Simple detach/reconnect returns control when no other controller exists; concurrent watching can be deferred from the first one-job persistence prototype.

Optional explicit session control lock is a later proposal: other Backslash attachments to that same session view output but cannot inject text or control keys. While locked, takeover needs the current owner's release/approval rather than unconditional Take control. Disconnected-owner recovery/lease behavior remains an explicit policy choice. This is input ownership, not OS process/file isolation; another same-account/admin shell may still signal the process or modify files under OS permissions. Do not promise protection against those paths.

Optional future **Who's connected** presence is separate from same-session attachment roles. Participating Backslash clients could opt into registration/heartbeats with an authorized server broker/helper. Distinguish authenticated identity from friendly/self-asserted labels and shared-account limitations, apply remote admin/visibility policy, mark stale/offline presence and keep commands/output/session details private unless explicitly shared. Joining a session requires an explicit authorized request. Cross-account visibility needs an enforcing broker, not scanning private processes/files; no network-wide discovery or inference that every SSH client is Backslash. No presence system is implemented or contacted here.

## Presence phases and endpoint-triggered identity

Presence and managed access are successive phases. **Phase 1** is an opt-in toggle for participating Backslash clients on the same host, using authorized registration/heartbeats. Friendly device/person labels can aid recognition but must be marked unverified unless tied to an authenticated identity. Shared SSH accounts do not distinguish humans by themselves. Stale/offline presence is explicit; private commands, output and session details stay separate. Presence visibility grants neither session output access nor control. Joining is a deliberate request checked against the session's authorization.

**Phase 2** is later organization-managed gatekeeping. Show Managed by organization and the enforcing policy/provider, with server/gateway authorization and administrator-approved visibility across accounts. A local password/toggle, client declaration, hostname/IP or port convention cannot enforce access across alternate SSH clients/routes. Enforcement must cover the host/gateway authentication paths it claims to govern. Do not scan private files/processes to infer cross-account presence.

Candidate workflow: an endpoint requiring organization identity initiates browser or native sign-in/self-enrollment. Keep a stable provider-issued account subject distinct from revocable/rotating credentials and a separate enrolled device ID. Repeat sign-in should resolve the same account; enrolling another device does not invent another person. A self-generated local ID/friendly label remains an unverified identifier. Provider trust, enrollment/verification protocol, secure credential storage, recovery, revocation, administrator policy and integration with SSH authentication remain research decisions. No identity provider, organization policy or presence service is implemented or contacted.

Reconnection may return control only after the remote owner confirms that no other controller owns the same session. If another controller exists, show the confirmed role and require the defined transfer/owner-approval path. First prototype can defer multiple viewers; simple detach/reconnect and completed-result recovery are still required. Optional lock and disconnected-owner recovery policy must be stated before collaborative attachments are offered.
