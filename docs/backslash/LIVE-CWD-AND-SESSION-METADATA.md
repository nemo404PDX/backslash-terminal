# Live cwd repair and session metadata design

Status: scoped implementation validated, 2026-10-15. Listing conveniences and the richer metadata model below are **design only**. No status bars, file transfers, command history, remote integration, or listing behavior is added by this repair.

## Current repair

The e0d3b2a7 build fixed launch identity, but still required manual folder confirmation after navigation. That does not satisfy **Pin current folder**. The current repair installs a session-local integration when Backslash starts a plain interactive local PowerShell 7 process. It appends `-NoExit -EncodedCommand` to the physical process command line, after the existing environment expansion. The logical command line returned by the connection and frozen by ControlCore remains the profile's original command line. Restart/duplicate therefore do not accumulate bootstraps or turn the launcher into an unknown advanced command.

Only direct `pwsh`/`pwsh.exe` with the existing conservative simple-flags whitelist is eligible. Noninteractive forms, Windows PowerShell 5.1, `-Command`, `-File`, existing encoded commands, remote PowerShell options, developer-shell wrappers and unknown arguments are untouched. Unsupported forms can provide their own reports or use the separate **Add a folder...** action. Existing running sessions are not retrofitted and receive no surprise input. No persistent profile, execution policy, user SSH configuration or remote shell is changed.

The bootstrap runs after normal PowerShell profile startup. Its version and FullLanguage checks fail closed; a namespaced session marker makes installation idempotent. It chains the existing `LocationChangedAction`. Cwd comes from the FileSystem provider's `PathInfo.ProviderPath`, including custom filesystem PSDrives. `$PWD` is runspace/provider state; a Windows process working directory, environment expansion, profile starting folder or rendered prompt cannot supply the same information. Registry and other providers produce an empty/unknown cwd.

The integration retains the existing `PSConsoleHostReadLine` function and wraps that input boundary. It reports the current provider path when that function is entered, after the **original prompt** has run, and clears the report in `finally` before a submitted line executes. The location handler clears while execution is in progress. At the next input boundary the path is refreshed. This prevents a parent's last cwd remaining usable during an ordinary nested shell, SSH/WSL command or full-screen program. The prompt itself is never replaced, so its text, `$?` and `$LASTEXITCODE` observations are preserved. Existing readline behavior and the prior location handler are called once. Profiles that replace these hooks later, bypass normal console readline, or invoke unusual nested prompts require their own integration; no universal PowerShell command-state detector is claimed.

The existing OSC `9;9` channel carries the observation. `AdaptDispatch::DoConEmuAction` now treats the complete suffix after the action separator as a path, preserving semicolons inside quoted and unquoted paths. Empty, invalid, excessive or control-containing reports invalidate the previous observation. The parser retains otherwise-discarded controls specifically in cwd payloads for that validation and invalidates cancelled/aborted cwd frames; other OSC actions retain their existing behavior. The source rejects C0/C1 controls (including ESC/BEL/NUL/CR/LF); Unicode, spaces, apostrophes and semicolons are preserved. The public reported-directory getter returns unknown after disconnect. Connection replacement or a disconnected/connecting state also resets the sticky reported flag, so reconnect cannot revive a previous generation. Duplicate identical emissions are coalesced, and an overlong physical command line falls back to the untouched logical launcher. **Pin current folder** requires a usable reported path; manual entry is an explicitly separate action. A pin stores a fixed copied descriptor, so navigating afterward never updates an earlier pin.

Legacy OSC output is **unverified application output**, not an authenticated host assertion. A child can emit its own cwd/control sequences, overwrite an observation, or spoof shell readiness. Launch GUID/source/host preflight prevents unrelated profile reuse but cannot authenticate output produced inside that session. Clearing before execution addresses stale parent values; it does not identify the actual producer of every report. A remote or nested program reporting a Windows path must not be interpreted as proof that it belongs to the local host. Current local pin capture still validates the fixed path and local existence; consumers needing trustworthy remote host context must wait for the context model below. Do not use cwd/status as authorization or as permission to send commands.

Windows paths containing literal percent tokens remain unsupported by the fixed local pin launcher, which already expands environment strings; metadata itself is never environment-expanded. OSC `9;9` is a raw path convention, not a URI. `OSC 7` is currently ignored in this codebase; `OSC 633` handles completions here and is not a replacement cwd transport. Shell integration over SSH/WSL needs a cooperating shell on that side. This repair starts no SSH connection or WSL process.

## Reusable metadata path

```text
shell integration -> PTY / SSH transport -> VT framing and dispatch
                  -> per-pane engine/session metadata -> consumers
```

Keep three interfaces distinct:

| Interface | Contents and ownership | Restrictions |
| --- | --- | --- |
| Output text | Process bytes decoded through the existing incremental VT parser into the terminal buffer | Never scrape prompt text to derive cwd, host, commands or success. |
| Structured metadata | Bounded parsed observations stored with the pane's connection/session state | Carries provenance, context and validity; cannot execute anything. |
| Input/command submission | Explicit user typing or an independently authorized action delivered through the input path | Never triggered by a cwd/status update or treated as an implicit response to output. |

The connection transports bytes, handles connection lifetime and establishes the local launch context. It should not maintain an independent shell parser. VT dispatch owns framing/validation. The engine owns one coherent pane/session metadata snapshot. ControlCore exposes that snapshot; Pins, a future status bar and a future file-transfer starting-folder picker consume the same API. UI chrome does not ask a process for its cwd or reinterpret decorated titles. Metadata follows cached pane content during moves, rather than attaching to a tab label or settings draft.

A future snapshot should include connection/session ID and generation, context ID and optional parent context, launch host/profile identity, reported host/user/shell, negotiated integration version and capabilities, cwd value/path kind/provider/URI authority, provenance, monotonic revision and last-observed time, and validity/reason. Separate `ProfileSeed`, `ReportedUnverified`, `ContextReported` and `UserConfirmed`; confidence must never silently promote a seed or an unauthenticated report into verified identity. URI authority supplied by output is a claim. A context ID or nonce can reduce accidental cross-talk; same-session processes can read or forge it, so it is not an authorization token.

Use explicit state transitions: `Unknown -> PromptReady -> Executing -> PromptReady`, plus `Disconnected`, `UnsupportedProvider` and `ContextUnknown`. Clear actionable cwd on connection generation changes, reconnect, entering a child context, execution that can change context, malformed reports and capability loss. A child context must announce itself and restore its parent explicitly, with matching generation and ordering; an old parent value must not automatically reactivate just because a child stops emitting. An ordinary local shell launching SSH cannot infer the remote context from its process name or prompt. Without cooperating markers, show unknown and offer explicit manual entry. Full-screen/alternate-buffer state is an additional reason to avoid treating a report as an idle shell, not a way to discover cwd. Refresh on a real prompt boundary; a timestamp alone cannot prove readiness.

For richer protocols, specify a versioned frame and an allowlist of fields/capabilities before enabling consumers. Decode incrementally across arbitrary transport chunk boundaries. Use a single unambiguous escaping scheme (for example bounded UTF-8 JSON inside an explicitly delimited extension) rather than naive delimiter splitting. Enforce maximum frame/field sizes, collection counts and nesting depth; reject embedded controls and invalid Unicode. Existing OSC framing terminates at BEL/ST: an embedded terminator cannot be distinguished from the end of a frame, so producers must reject or encode it before output. Unsupported/malformed extensions fail to unknown without leaking partial data into an actionable value. They do not change parser mode or accept input commands.

If OSC 7/file URIs are added, use an actual URI parser. Validate scheme, authority and path kind; percent-decode exactly once, retain Unicode correctly, distinguish Windows drives/UNC from POSIX paths, and reject NUL/controls after decoding. Do not environment-expand reported strings, normalize a remote path with local filesystem rules, convert an unverified hostname into a local path, or roundtrip through display text. Preserve native path and display form separately.

All application-emitted control sequences are untrusted. Metadata must not open files, enumerate remote directories, make network requests, change settings, apply credentials, or submit commands on arrival. Any consumer that acts on a path still validates its own host context, user intent, access and operation. Future file-transfer selection requires separate authorization and transport decisions. Never infer security from a successful exit status, capability flag or cwd report.

Bound updates by parser limits and per-connection memory. Replace/coalesce redundant state, publish a revision only for changes, marshal a coalesced latest snapshot to the UI, and keep filesystem/network queries out of the output hot path. Avoid one UI task or event-history record per output chunk. Set a bounded publication rate for noisy extensions and drop invalid/oversized updates without retaining arbitrary payloads. Lifetime/reset notifications must outrank queued stale observations.

## Future command boundaries and history

A later shell integration slice may announce prompt start/end, submitted-command start, completion and optional status with context/generation and a command ID. Record command text only from an explicitly supported shell integration or authorized submission interface; terminal output and displayed prompt strings are unsuitable. Distinguish absent, PowerShell success/failure, native exit code, cancellation and incomplete/disconnected commands. `$?` and `$LASTEXITCODE` are different signals; stale native exit codes must not label a succeeding PowerShell command as failed. Pipelines and nested execution require stated semantics.

Success-filtered history can then consume a bounded, opt-in command record after matching completion. It must exclude unknown/interrupted records according to policy, handle multiline/Unicode without executable rewriting, avoid recording secrets automatically, and keep retained command text separate from cwd/status. This repair does not implement command capture, exit-status reporting, replay or history persistence.

## Separate future listing slices

These ideas are documented at the user's request and **are not implemented**:

* An opt-in per-profile PowerShell hidden/system listing preference can add `PSDefaultParameterValues['Get-ChildItem:Force']=$true` only in newly launched sessions. Preserve unrelated dictionary entries, existing user wildcard defaults and its `Disabled` flag; surface conflicts rather than silently replacing user intent. Explicit `-Force:$false` wins. This affects some scripts, functions and recursive calls too; it is not guaranteed to be interactive-only and does not bypass access controls. No persistent profile or global setting change is implied.
* A separate new-session cmd option could merge `DIRCMD=/a` into the child's environment while preserving unrelated switches and surfacing preexisting attribute-filter conflicts. The independent reviewer verified `dir /-a` overrides it in an owned fixture. It has no effect on PowerShell, native `ls`, WSL or SSH listings.
* Optional Unix conveniences should be a session function library, initially `ls` with `-a`, `-l`, `-h`, `-lah` and `--`. An alias cannot translate arguments, and the stock `ls -> Get-ChildItem` alias takes precedence over a function. Replace only that recognized stock alias; preserve custom/read-only/native conflicts and offer a namespaced helper when skipped. Parse flags explicitly, report unsupported flags clearly, and use structured splatting into module-qualified `Get-ChildItem`; no `Invoke-Expression` or command-string rewriting. Define wildcard versus literal semantics, multiple paths, Unicode/spaces/apostrophes and leading dashes. Keep FileInfo/DirectoryInfo objects and numeric Length in the pipeline. Human/long rendering belongs in a wrapper-specific view/formatting metadata, not `Format-Table`/`Out-String` inside the helper. Describe Unix appearance as approximate. Defer cp/mv/rm and POSIX grammar. Functions can affect scripts; keep this feature's flags and failure behavior separate from cwd reporting.
