## Confirmed mechanism mismatch

The new controls only create classic static verbs. They cannot satisfy the Windows 11 primary-menu requirement. Microsoft documents a native `IExplorerCommand` COM handler, `windows.comServer` registration and `windows.fileExplorerContextMenus` associations for selected `Directory` and `Directory\Background`, with app identity. Unpackaged applications can use a sparse identity package. This is a different integration mechanism, not a registry refresh problem. [Microsoft context-menu integration guide](https://learn.microsoft.com/en-us/windows/apps/desktop/modernize/integrate-packaged-app-with-file-explorer).

## Reusable source and portability hazard

The fork already contains `ShellExtension/OpenTerminalHere.h/.cpp`, implementing `IExplorerCommand` and `IObjectWithSite`, selection/background resolution, filesystem filtering, title/icon methods and direct `CreateProcessW`. `CascadiaPackage/Package.appxmanifest` declares the matching COM surrogate and both folder contexts. The portable includes `WindowsTerminalShellExt.dll`, but copying a DLL is not package registration. Its current invocation uses ordinary `-d`, and its class identifiers/package publisher retain upstream Windows Terminal identities. These must not be installed unchanged or reused to replace Windows Terminal's menu. The adapted handler must use Backslash's literal-folder dispatch, dedicated stable identities and Backslash resources.

Attaching sparse identity directly to `Backslash.exe` is not a drop-in solution. `TerminalSettingsModel/FileUtils.cpp::GetBaseSettingsPath` selects adjacent settings only for `!IsPackaged() && IsPortableMode()`. `WtExeUtils.h::IsPackaged` checks actual package identity. Adding identity can change storage/routing and disables today's unpackaged-only management controls. Adjacent settings and profiles must remain unchanged.

## Recommended architecture (proposal, not deployed)

Use a small separate Backslash integration host and native handler, with a sparse package identifying that host rather than the main portable executable. Keep one stable per-user support location, one package/COM identity and one owned target configuration. Explicit **Use this copy** updates the selected target path; merely launching a different build never retargets it. The handler obtains the selected folder/background from shell interfaces and launches the exact target with the literal-folder argument and no command-shell intermediary.

This preserves portable-copy selection without reinstalling the helper package for every app build. Missing targets produce an actionable error. Repair checks package/handler/target state independently. Remove targets the exact Backslash package family/publisher and owned configuration; it must work even after the portable copy is deleted. Migration of the two existing classic keys is a separately confirmed owned cleanup, not automatic removal.

This is a small installed support component, not a zero-registration ZIP-only feature. A package's external location ties it to a folder; moving that support folder needs repair. Main-executable package identity and child-process behavior must be verified in the prototype before claiming portable isolation. Microsoft documents desktop child-process package policy separately; do not assume package identity cannot propagate. [Process attribute reference](https://learn.microsoft.com/en-us/windows/win32/api/processthreadsapi/nf-processthreadsapi-updateprocthreadattribute).

The alternative is a fully packaged Backslash with its own identity/signing and a deliberate storage/migration design. That is broader than the requested portable integration. Classic verbs are not offered as a completed fallback for this request.
